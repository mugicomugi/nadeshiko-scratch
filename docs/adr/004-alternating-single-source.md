# ADR-004: 編集モデルは交替単一正本

- **状態**: 提案中（Phase 0 の S-18 / S-20 で確定）
- **日付**: 2026-09-16

## 状況

ブロックとテキストの**双方向**編集を初日から提供する（ユーザー決定）。両方を編集可能にすると「どちらが正本か」という問題が必ず出る。

## 決定

**交替単一正本（alternating single source of truth）。** MakeCode が採る方式。

- プロジェクト文書に `primary: 'blocks' | 'text'` と `syncState` を持ち、**両表現を保存する**
- `primary` は**そのペインで実際に編集イベントが起きたときのみ**遷移する
- ブロックへ切り替えるとき、保存済みワークスペースから生成したテキストと現テキストを **AST 正規形**で比較する。一致するなら decompile せず保存済みワークスペースをそのまま表示する（座標・浮きブロック・折りたたみが保存される）。不一致なら decompile し、`oldWorkspace` をヒントに構造パスが一致するブロックの ID と座標を再利用する

## 却下した代替案

| 案 | 却下理由 |
|---|---|
| **単一正本＝ブロック**（v0.1 の nadeshiko フィールドは参考表示用） | テキストが正本になりうるので成立しない |
| **単一正本＝テキスト**（ブロックは投影） | ブロック座標・浮きブロック・折りたたみが毎回失われる。子どもが並べた位置が勝手に変わるのは受け入れられない |
| **双方向データフロー + 操作変換** | 実装コストが桁違い。単一ユーザーの単一セッションに OT は過剰 |

## 影響

- 逆変換エンジンは **`nako_ast.mts` の NodeType 全52種**に対して処理を定義し、未定義なら `raw_nako` にフォールバックして例外を投げない（**全域性**）
- **CI で3つの往復契約を強制する**: 契約A `blocks→text→blocks'` ／ 契約B `text→blocks→text'` ／ 契約C `text→AST→text'`
- 「戻せない」ケースの UX が製品品質を決める。**破壊的 discard を作らない**（履歴への push で必ず取り消せる）
- マニフェストに `decompile.match` フィールドを最初から含める（後付けすると全エントリ見直しになる）

## 再評価トリガー

- S-20 の raw ノード比率が 50% 超 → Phase 2 予定の `switch` / `try_except` / `def_func` のブロック化を Phase 1 に前倒し
- S-18 の再パース同値率が 99% に届かない → トークン index 範囲からの復元（第1.5段）を追加

## Phase 0 で確定させること

- [ ] S-18: `raw_nako` の原文範囲。全ノードの spanOf() で切り出した原文を単独で parse() し直し、元の部分木と canonAst 同型になる率 **99% 以上**
- [ ] S-20: Phase 1 の36 NodeType + `raw_nako` 3種で、公式コーパス全件に対する decompile 成功率 100%、契約B成立率 100%、raw 比率 30% 以下
