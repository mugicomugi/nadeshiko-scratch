# ADR-002: ガード注入は実行直前の AST パスで行う

- **状態**: 提案中（Phase 0 の S-15 / S-19 で確定）
- **日付**: 2026-09-16

## 状況

無限ループ・暴走コードを止める必要がある。当初案（統合ドラフト v0.1）は「**生成器が**ループ本体の先頭にガード命令 `実行安全チェック` を注入するので注入漏れがない」だった。

これは2つの理由で破綻する。

1. **テキスト編集を初日から開放する**（ユーザー決定）。手書きのループは生成器を通らない
2. ガードの throw は `エラー監視` に握り潰される。`nako_gen.mts` の `convTryExcept` は**素の try/catch で再 throw フィルタがない**（依存面 I5）

## 決定

**ガード注入は生成器ではなく、実行直前の AST パスで行う。** 実行直前の順序を固定する:

    parse → audit → injectGuards → print → 再parse → 再audit → 送信

- `try_except` を GUARDED 対象に加え、**try / except の両ブロック先頭に注入**する。停止フラグが立っていれば except 先頭のガードが無条件で再 throw する
- `実行安全チェック` は `asyncFn: true` で実装し、**行番号とスレッドIDを引数で受け取る**。通常は解決済み Promise を返し、`performance.now() > frameDeadline` のときのみ実マクロタスクを譲る
- **ガードとスケジューラは単一の `frameDeadline` を共有する**（独立した2つの12msタイマーを持たない）
- 再 audit が落ちたら実行しない。telemetry に送り、子どもには「うまく じゅんびが できませんでした。もういちど おしてね」と出す

ガード注入で行番号がずれるため、**`PrintMap`（実行用テキスト行 ⇄ 編集テキスト行 ⇄ ブロックID の3段写像）をプリンタの必須出力にする**。これがないと実行中行ハイライトとエラー行表示が両方壊れる。

## 却下した代替案

| 案 | 却下理由 |
|---|---|
| **生成器での注入**（v0.1） | テキスト編集の開放で破綻する |
| **debugOption.useDebug 常時** | 全行が await 化され性能が出ない。**ただし S-19（契約Cプリンタの同型率100%）が No-Go ならここへ退避する**。「ゆっくり実行」「ステップ実行」では使う |
| **acorn/astring で生成JSを後段トランスフォーム** | `nako_gen` の出力形式への依存が増え、バンドルも増える |
| なでしこ本体のフォーク | ADR-008 の条件を満たさない |

## 影響

- プリンタ（契約C）が**実行経路に載る安全クリティカル部品**になる。見積りは 4〜5人週（当初の2人週は過少）
- `ずっと繰り返す` を提供できる（v0.1 は「無限ループブロックを提供しない」で回避していた）が、ギャラリーが成立するには必要

## 再評価トリガー

- S-19 の契約C同型率が 100% に届かない → `useDebug` 常時へ切替（**実行モードが変わるので Phase 0 の時点で決断が要る**）
- I5（`convTryExcept` が素の try/catch）が上流で変更された → 再 throw 設計を見直す
