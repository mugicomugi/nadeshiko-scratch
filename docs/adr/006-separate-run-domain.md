# ADR-006: 実行オリジンは別レジストラブルドメイン（kotoba-run.jp）

- **状態**: 提案中（S-27 の実地確認で最終判断）
- **日付**: 2026-09-16

## 状況

統合ドラフト v0.1 は実行オリジンを `run.<domain>` のサブドメインとし、「テキスト編集の開放」または「親ドメインでの認証Cookie導入」を別ドメインへの移行トリガーとしていた。

**この2つのトリガーが両方とも初日に発火する**（テキスト編集は Phase 1、認証は Phase 2）。さらに第3のトリガーが加わった: **公開ギャラリー＝他人のコードを自分のログインセッション下で実行する**。

## 決定

**実行オリジンを別レジストラブルドメイン `kotoba-run.jp` に置く。**

ドメイン構成は**レジストラブルドメイン2本＋サブドメイン3本**。分割の軸は「機能」ではなく **(1) Cookie の到達範囲 (2) URLフィルタで個別遮断したい単位** の2つ。

## 根拠

1. **Cookie は同一オリジンポリシーに従わず、登録可能ドメイン単位で共有される。** `run.kotoba-blocks.jp` を制御できる攻撃者は `Domain=kotoba-blocks.jp` の Cookie をセットして親の Cookie を上書きできる（cookie shadowing）。`__Host-` 接頭辞で緩和できるが、「緩和策で守る」より「攻撃面を構造的に消す」ほうが子どもの認証情報を扱うサービスとして正しい
2. **公開ギャラリーで他人のコードを実行する。** 脅威が「自分のミス」から「意図的な攻撃」に変わった
3. sandbox 属性の設定ミス1つ（`allow-same-origin` の誤付与）が致命傷にならない
4. Safari ITP / Storage Access / Related Website Sets の将来の挙動変化を追わなくてよい

あわせて **API は SPA と同一オリジンに置く**（`api.` サブドメインにしない）。`__Host-` は Domain 属性を禁じるため、API を別サブドメインに置くと SPA の JS から CSRF トークン Cookie が読めず double-submit が実装不能になり、全状態変更リクエストが CORS preflight を誘発する。

## 却下した代替案

| 案 | 却下理由 |
|---|---|
| **run. サブドメイン**（v0.1） | 移行トリガーが3つとも初日に発火する |
| **API を api. サブドメインに** | CSRF double-submit が実装不能、CORS preflight で Worker リクエストが倍増 |
| **学校向けを最初から別ブランドで並行運用** | ユーザー決定「学校と個人の両方を最初から」への実質的な回帰。運用・教材・サポートが二重化し1〜2名では維持できない。**部分採用**として `kotoba-school.jp`（ギャラリー非搭載ビルド）を Phase 4 の DoD に置く |

## 影響（逃げずに書く）

**学校の URL フィルタ申請が 1件 → 2レジストラブルドメインに増える。** これは現場の採用可否に直結する実害。

緩和策:

- **前方一致しやすい命名** — `kotoba-blocks.jp` と `kotoba-run.jp`。多くのフィルタ製品は前方一致・部分一致を持つため `kotoba-` の1エントリで通る可能性がある（ワイルドカードを許さない設定のフィルタが実在するため、`run.` サブドメインよりむしろ1エントリに収まりやすい場合がある）
- `/school/network` から A4 1枚の申請書 PDF を自動生成
- `/school/check` で両ドメインへの到達性を自己診断し、失敗したら原因と対処を明示する（**原因不明の白画面で終わらせない**）
- オフライン配布パッケージ（ただし同一オリジンになるため隔離が失われる。専用 allowlist と保護者向け説明を別立てで書く）

## 再評価トリガー

- S-27 で「2ドメインを1エントリで許可できない」学校が多数 → `kotoba-school.jp`（ギャラリー非搭載ビルド）を Phase 4 の**必須**成果物に昇格
- ブラウザが Related Website Sets 等で cookie shadowing を構造的に解決した → サブドメインへの回帰を検討
